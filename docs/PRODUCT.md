# 여백 Product Notes

> 이 문서는 구현 세부사항보다 **제품 의도와 판단 기준**을 보존하기 위한 문서다.  
> Codex나 다른 모델이 이후 작업을 이어갈 때는 `README.md`와 함께 이 문서를 먼저 읽는다.

## 1. 제품 한 줄 정의

**여백은 하루를 빽빽하게 최적화하는 일정 앱이 아니라, 사용자가 중요하다고 정한 1~2가지를 지키기 위해 필요한 조사와 안전장치만 마련하고 나머지는 일부러 열어두는 계획 도구다.**

핵심 문장:

> 계획은 실패를 없애기 위해서가 아니라, 중요한 것을 지키기 위해 세운다.

또는:

> 중요한 것만 챙기고, 나머지는 흘러가는 대로.

---

## 2. 처음 발견한 문제

데이트나 하루 나들이를 계획할 때 실제 계획자는 다음을 계속 오간다.

- 캘린더
- 지도
- 블로그 / 후기
- YouTube
- 공식 홈페이지
- 박물관·미술관 사이트
- 티켓 / 예약 사이트
- 메신저

문제는 단순히 “갈 곳을 추천받기 어렵다”가 아니다.

**중요한 목적을 성공시키는 데 필요한 정보와 제약이 여러 곳에 흩어져 있고, 사용자가 그것을 직접 조사하고 머릿속에서 조합해야 한다.**

여백은 이 조사 노동을 줄이는 것이 핵심이다.

---

## 3. 세 역할

### 사용자

사용자는 판단한다.

- 오늘 무엇이 가장 중요한가
- 무엇을 반드시 지키고 싶은가
- 무엇은 다른 것으로 대체해도 되는가
- 어떤 불편은 피하고 싶은가
- 무엇은 굳이 미리 정하지 않아도 되는가

사용자가 제공해야 하는 것은 **판단과 선호**다.

### 애플리케이션

애플리케이션은 판단을 구조화한다.

- Anchor
- Priority
- Guardrail
- Backup
- Transport
- Flexible / 여백

그리고 AI가 조사할 수 있는 명확한 입력으로 만든다.

### AI

AI는 **planner가 아니라 research assistant**다.

AI의 역할:

- 최신 웹 정보 조사
- 운영시간 / 휴무 / 예약 / 브레이크타임 확인
- Anchor를 위협하는 위험 발견
- 대체 가능한 Anchor의 Backup 조사
- Priority 관련 정보 조사
- 출처 제시
- 모르는 것은 미확인으로 남기기

AI가 하면 안 되는 것:

- 사용자의 중요도를 마음대로 변경
- Anchor를 더 “좋아 보이는” 다른 장소로 임의 교체
- 사용자의 여백을 전부 일정으로 채우기
- 검색하지 않은 최신 정보를 아는 척하기

## 4. 핵심 계획 모델

### Anchor

**오늘의 성공 여부를 결정하는 핵심 목적. 최대 1~2개.**

예:

- 화성행궁을 충분히 관람한다.
- 맛있는 음식을 먹는다.

Anchor는 반드시 특정 장소일 필요가 없다.

#### 장소 고정형 예

`화성행궁 제대로 보기`

- 특정 장소가 중요
- 대체 불가
- 운영시간에 영향받음
- 충분한 체류 중요

#### 목표 달성형 예

`맛있는 음식 먹기`

- 로우파이브가 후보일 수 있음
- 그 식당 자체는 필수가 아님
- 다른 좋은 식당으로 대체 가능
- Backup 필요 가능

---

### Priority

Anchor만큼 하루 전체의 성공 조건은 아니지만 **꽤 중요하다.**

“되면 좋고 아니면 말고” 수준으로 취급하지 않는다.

첫 검증 사례의 예:

- 가챠샵
- 박물관
- 소품샵

계획을 만들 때 적극적으로 포함을 시도하지만, 일부가 빠진다고 하루 전체가 실패한 것은 아니다.

---

### Guardrail

Anchor를 망치거나 사람을 지나치게 힘들게 만들 수 있는 제약.

예:

- 너무 많이 걷지 않기
- 최대 웨이팅 시간
- 너무 늦은 귀가 피하기
- 출퇴근 혼잡 피하기
- 예산
- 날씨 민감도

가능하면 boolean / enum / number / time 등 구조화된 값으로 받는다.

**미정은 정상 값이다.**

---

### Backup

Anchor가 대체 가능한 경우에 준비하는 대안.

예:

- Anchor: 맛있는 음식 먹기
- Plan A: 로우파이브
- Backup: 주변 식당
- 전환 조건: 휴무 / 너무 긴 웨이팅 / 예약 불가 등

Backup은 모든 Anchor에 필요하지 않다.

`EXACT` Anchor에 억지로 대체 장소를 추천하지 않는다.

---

### Transport

단순히 `현재 위치 → 목적지` 경로만 보는 것이 아니다.

여러 사람이 다른 장소에서 출발할 수 있다.

고려 요소:

- 참여자별 출발지
- 같이 출발 / 중간 합류 / 현지 합류
- 이동시간
- 환승 수
- 혼잡
- 비용
- 한 사람에게 이동 부담이 과도하게 몰리는지

지도 앱을 대체하려는 것은 아니며, **계획의 조건을 구조화하는 역할**이 우선이다.

---

### Flexible / 여백

의도적으로 정하지 않는 영역.

예:

- 정확한 체류시간
- 카페 갈지 여부
- 산책 경로
- 정확한 귀가시간
- 현장에서 발견한 장소

빈칸은 미완성이 아니다.

**“현장에서 결정”도 하나의 완성된 계획 상태다.**

---

## 5. 입력 UX 원칙

초기 구현이 자유 텍스트 위주라 “메모장”처럼 보이는 문제가 있었다.

따라서:

> 계획 판단에 필요한 정보는 구조화해서 받고, 설명하기 어려운 부분만 자유 메모로 받는다.

대략적인 방향:

- 구조화 입력 80%
- 자유 메모 20%

단, 모든 것을 폼으로 만들면 안 된다.

**모바일에서 약 3~5분 안에 계획 하나를 만들 수 있어야 한다.**

---

## 6. AI 조사 UX 원칙

AI 기능의 핵심 액션은 하나다.

**`계획 조사하기`**

AI 채팅창이 제품의 중심이 아니다.

조사 결과는 긴 에세이 하나보다 다음처럼 구분한다.

- Anchor 확인
- 위험 / 충돌
- Backup
- Priority 관련 조사
- 미확인
- 여백
- 출처

최신성이 중요한 정보는 실제 웹 검색 근거가 있어야 한다.

검색 근거가 없으면 조사 성공으로 취급하지 않는다.

정보가 충돌하면 임의로 하나를 고르지 말고 **충돌 상태를 표시**한다.

계획의 의미 있는 입력이 수정되면 기존 조사 결과는 **재조사 필요(stale)** 상태가 된다.

---

## 7. 조사 신뢰성 원칙

우선순위:

1. 공식 홈페이지
2. 공식 SNS / 공식 예약 페이지
3. 지도 / 신뢰 가능한 플랫폼
4. 후기성 자료

표시할 수 있으면:

- 출처
- URL
- 조사 시각
- 미확인 여부
- 정보 충돌 여부

를 보여준다.

출처가 있다고 사실을 100% 보장하는 것은 아니다.

---

## 8. 공유 경험

Planner와 Companion은 필요한 정보량이 다르다.

### Planner

보고 싶은 것:

- 구조화된 판단
- 이동 조건
- 조사 결과
- 위험
- Backup
- 출처

### Companion

필요한 것은 훨씬 간단할 수 있다.

예:

- 언제 / 어디서 만나는지
- 오늘의 핵심
- 대략 어떤 곳을 가는지
- 중요한 날씨 변수나 준비사항

따라서 공유 화면은 계획자 화면보다 단순하게 유지한다.

출발지, 개인적인 이동 메모, AI 조사 내부 결과 등은 기본적으로 공유 화면에 노출하지 않는다.

## 11. v0.1 성공 기준

제품 완성도가 아니라 실제 사용 여부로 판단한다.

성공 기준:

- 공개 URL이 존재한다.
- 실제 계획을 생성할 수 있다.
- 구조화된 선호가 저장된다.
- AI에게 실제 웹 조사를 맡길 수 있다.
- 출처와 Backup을 확인할 수 있다.
- 공유 링크를 동행자에게 보여줄 수 있다.
- 실제 약속에서 사용해본다.
- 사용 후 최소 한 번은 피드백을 반영한다.

핵심 질문:

> 이 앱을 쓰면서 내가 직접 검색해야 하는 일이 실제로 줄었는가?

## 12. 변경 판단 기준

향후 기능 추가나 리팩터링 전 아래 순서로 판단한다.

1. 이것이 Anchor를 지키는 데 도움이 되는가?
2. 사용자의 조사 노동을 줄이는가?
3. 사용자의 판단을 대신하려는 기능은 아닌가?
4. 여백을 불필요하게 없애지는 않는가?
5. 실제 사용에서 필요성이 확인됐는가?
6. 지금 구현해야 하는가, 아니면 TODO로 남겨도 되는가?

특히 새로운 기능 때문에 앱이 다시
“AI가 알아서 완벽한 데이트 코스를 짜주는 서비스”
쪽으로 가면 제품 방향에서 벗어난 것이다.

## Decision Log

### 2026-10-07 / 10-08

- 자유 텍스트 중심 v0.1은 메모장에 가까워질 위험이 있다고 판단했다.
- 핵심 판단 데이터를 구조화하고 자유 메모는 보조로 제한하기로 했다.
- AI를 planner가 아닌 research assistant로 정의했다.
- Anchor는 최대 1~2개로 유지한다.
- Priority는 단순 Optional보다 높은 중요도를 가진다.
- “정하지 않음”을 정상적인 계획 상태로 인정한다.
- AI 조사에는 실제 Google Search grounding을 사용한다.
- 검색 근거가 없으면 성공한 조사로 저장하지 않는다.
- 실제 사용자 테스트 전에는 기능 확장을 최소화한다.

### 2026-10-08 / 브라우저 내 계획 목록

- 일회성 링크 보관에서 벗어나 홈에서 저장한 계획을 다시 찾을 수 있게 한다.
- 현재는 로그인·기기 간 연동 없이 같은 브라우저에서 목록과 수정 권한을 보관한다.
- 계획 내용은 서버 DB에 유지하고, 지난 계획도 목록에서 제거하지 않는다.
- 기존 계획은 수정 키로 열면 목록에 추가한다. 공유 링크 열람만으로 추가하지 않는다.
- 후기·사진 등 기록 앱 기능은 이번 범위에 포함하지 않는다.

### 2026-10-08 / 실제 사용 피드백 반영

- Anchor의 충분한 체류·최소 체류 입력은 제거하고 보충 메모로 받는다. 기존 데이터는 보존한다.
- Priority의 중요함/매우 중요함 선택은 없앤다. Priority 자체가 중요한 후보라는 뜻이다.
- 시각은 24시간제 텍스트 입력과 지우기 버튼을 사용한다. 시작/종료 역전과 특정 시각 누락 오류를 구분하며 입력 옆에서 검증한다. 날짜를 넘기는 Anchor 시간 범위는 이번 범위에서 지원하지 않는다.
- 도보는 미정/이동 줄이기와 선택 메모로 받는다. 기존 도보 선택은 보존하되 무제한 보행 허용으로 해석하지 않는다.
- 귀가는 미정/정한 시각/막차로 구분한다. 막차 귀가 도착지는 선택 입력이며 계획자에게만 표시한다. 출발역을 도착지라고 가정하지 않는다.

### 2026-10-09 / 선택 중심 입력

- 새 계획의 제목은 날짜·지역으로 자동 생성하며 직접 수정할 수 있다.
- 목표, 지역, 후보, 웨이팅, 예산, 도보 메모, 여백, 시각에 자주 쓰는 선택지와 직접 입력을 함께 제공한다.
- 시각은 30분 단위 선택지를 제공하되 23:33 같은 세부 시각도 직접 입력하고 보존한다.
- 두 번째 목표, 후보, 불편 조건, 이동, 여백은 필요할 때 펼친다. 기존 값이 있는 항목은 자동으로 펼친다.
- 새 선택지를 고를 때만 연결된 유형을 채우며 기존 사용자 작성 내용은 임의로 바꾸지 않는다.
- JavaScript 미사용 시 기존 입력 폼으로 저장할 수 있다. DB와 조사 API 입력 구조는 유지한다.
